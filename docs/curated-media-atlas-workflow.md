# Curated Media Atlas Workflow

版本：0.1  
日期：2026-05-24  
适用范围：片单、书单、音乐史资料、艺术家资料、影像档案、展览资料、技术谱系等策展型资料网站。

## 1. 工作流目标

这个 workflow 用于把一批未完全清洗的研究资料，转化为可公开展示、可追溯、可继续扩展的策展型媒体档案项目。

它不是单纯的“做网页流程”，而是覆盖从资料盘点、事实核验、收录标准、数据模型、视觉参考、公开呈现、测试到发布的完整链路。

核心原则：

- 先核验资料，再设计展示。
- 先确定收录边界，再扩展片单、书单或作品清单。
- 公开页面使用读者语言，不暴露内部整理符号。
- 原始数据和公开呈现层分离。
- 对不确定信息显式标记，不编造。
- 用测试和清单防止后续迭代回退。

## 2. 适用场景

当用户提出以下类型任务时，可以使用本 workflow：

- 已有一批 Obsidian、Markdown、CSV、JSON 或截图资料，想整理为公开网站。
- 想把片单、书单、唱片单、艺术家资料或技术资料做成策展型档案。
- 需要先核验资料真实性，再决定如何展示。
- 需要把内部资料转成面向读者的项目页面。
- 希望做成“地图”“档案馆”“展览”“知识图谱”“观看路线”或“阅读路线”。

不适合的情况：

- 只需要快速生成一个简单列表。
- 用户已经有完全确定的数据和设计，只需要纯前端实现。
- 资料涉及隐私、未授权泄露或不能公开的内容。

## 3. 总体阶段

建议按 9 个阶段推进：

1. 资料盘点。
2. 主题范围与收录标准。
3. 事实核验与来源分级。
4. 数据模型和字段清洗。
5. 公开语言和 presentation layer。
6. 视觉参考研究。
7. 信息架构和交互原型。
8. 测试、防回归和质量检查。
9. 发布、复盘和 workflow 更新。

每个阶段都应该有明确输入、动作、输出和质量检查。不要跳过前 4 步直接做网页，否则很容易把不准确资料包装成漂亮界面。

## 4. 阶段一：资料盘点

### 输入

- 用户提供的资料目录或文件。
- 可能包含 Markdown、Obsidian note、CSV、JSON、图片、网页链接、视频链接、截图。
- 用户对项目的初步目标描述。

### 动作

- 使用文件搜索列出资料结构。
- 识别资料类型：事实字段、主观备注、待核验线索、图片素材、链接来源、内部任务。
- 统计候选条目数量。
- 找出明显问题：重复条目、乱码、缺字段、疑似误名、无法访问链接、截图未 OCR。
- 不在这一阶段做大规模改写，只建立全局认知。

### 输出

建议新增：

```text
docs/source-inventory-YYYY-MM-DD.md
```

文档应包含：

- 文件目录概览。
- 候选条目数量。
- 已有字段。
- 明显缺口。
- 高风险资料类型。
- 下一批核验建议。

### 质量检查

- 是否知道资料从哪里来。
- 是否区分了事实、备注和待核验线索。
- 是否发现重复或明显错误。
- 是否避免直接把原始资料当成最终数据。

## 5. 阶段二：主题范围与收录标准

### 输入

- 资料盘点结果。
- 用户对目标读者和主题边界的描述。
- 已有候选条目。

### 动作

- 定义项目主问题：这个档案到底帮助读者理解什么。
- 制定主目录、重要目录、延伸目录、相关议题的边界。
- 明确排除规则：哪些内容虽然相关，但不进入核心目录。
- 将内部等级翻译为读者语言。
- 明确标题策略：原名优先、成熟译名保留、不硬译。

### 输出

建议新增：

```text
docs/curation-criteria-YYYY-MM-DD.md
```

文档应包含：

- 项目主题句。
- 目标读者。
- 收录标准。
- 排除标准。
- 分级或分层说明。
- 标题和译名策略。

### 质量检查

- 是否能解释为什么某个条目进入主目录。
- 是否能解释为什么某个条目只适合延伸目录。
- 是否避免“所有相关内容都收进来”。
- 是否把内部代号改成读者能理解的语言。

## 6. 阶段三：事实核验与来源分级

### 输入

- 候选条目。
- 已有链接。
- 收录标准。

### 动作

- 逐条核验核心事实：原名、年份、作者或导演、出版方或发行方、片长或页数、主题。
- 按来源优先级查证，而不是只看搜索结果。
- 对每条关键信息保留来源。
- 对观看、购买、阅读或访问渠道单独记录，不与资料来源混用。
- 对用户上传、二级转载、平台聚合页标记可靠性。
- 对不确定字段使用空值或 `unknown`，不要补写看似合理的内容。

### 来源优先级

1. 官方来源：作者、片方、出版社、发行方、电视台、制片机构、官方网站。
2. 机构来源：电影节、图书馆、大学、博物馆、公共媒体、学术出版平台。
3. 平台来源：正规流媒体、书店、数据库、馆藏目录。
4. 数据库来源：IMDb、TMDb、WorldCat、Discogs、Wikipedia 等，只做辅助。
5. 用户上传和二级转载：只能作为线索，不能单独支撑关键判断。

### 输出

建议新增：

```text
docs/content-verification-method.md
docs/content-batch-XX-topic.md
docs/watch-or-access-channels-YYYY-MM-DD.md
```

每个批次文档应包含：

- 本批范围。
- 每条资料的核验结论。
- 已确认事实。
- 待确认问题。
- 来源链接。
- 是否进入核心目录。

### 质量检查

- 每个核心条目至少有一个可靠来源。
- 简介和判断不只来自数据库摘要。
- 用户上传不被写成官方渠道。
- 免费访问不等于公开放映或公开使用授权。
- 不确定信息没有被美化成确定表述。

## 7. 阶段四：数据模型和字段清洗

### 输入

- 已核验条目。
- 收录标准。
- 来源和访问渠道。

### 动作

- 设计可扩展 JSON 或表格结构。
- 区分源数据字段和公开展示字段。
- 清理内部备注、占位符、乱码和无效链接。
- 为图片、封面、截图建立本地资产路径。
- 为主题、人物、地区、技术、流派建立标准化数组字段。
- 为来源和访问渠道保留可靠性标签。

### 推荐字段

通用字段：

```text
id
title
original_title
display_title
year
creator
publisher_or_distributor
runtime_or_pages
summary
themes
genres
technologies
people
regions
languages
grade_code
collection_visibility
poster_or_cover
sources
access_channels
notes_internal
```

访问渠道字段：

```text
platform
url
access_type
source_kind
subtitle_or_language
reliability
public_use_status
checked_at
```

### 输出

建议新增或更新：

```text
data/items.json
assets/covers/
assets/presentation-data.js
tests/content-quality.test.mjs
```

### 质量检查

- JSON 可解析。
- 必填字段完整。
- `summary` 不为空，且长度符合项目要求。
- `sources` 与 `access_channels` 分开。
- 内部备注不进入公共 UI。
- 图片路径存在。

## 8. 阶段五：公开语言和 Presentation Layer

### 输入

- 清洗后的数据。
- 收录标准。
- 目标读者。

### 动作

- 建立 presentation layer，不直接在 UI 中解释原始数据。
- 将内部等级、状态、备注转换成读者语言。
- 限制每张卡片展示的信息量。
- 只展示成熟译名，不生成不可靠中文标题。
- 为主目录、延伸目录、相关议题建立公开可读标签。
- 将动态 UI 文案集中管理，便于后续 i18n。

### 示例规则

- `S / A / B` 不直接出现在公共页面。
- `permission_required` 显示为“授权待核验”或更自然的读者语言。
- `user_upload` 显示为“用户上传”，不能暗示官方授权。
- 原名优先，中文名作为副标题。
- 卡片标签最多 3-4 个。

### 输出

建议新增：

```text
assets/presentation-data.js
docs/public-copy-rules-YYYY-MM-DD.md
```

### 质量检查

- 公共页面不出现内部工作语。
- 标题、标签、按钮文案面向读者。
- 一部条目不会因为关键词泛化出现在过多路线中。
- presentation layer 有测试覆盖。

## 9. 阶段六：视觉参考研究

### 输入

- 项目定位。
- 当前原型或截图。
- 用户提供的参考案例。

### 动作

- 搜索并挑选 5-8 个优秀案例。
- 保存截图到项目目录。
- 分析每个案例的结构、交互、视觉语言和可借鉴点。
- 对比当前项目问题。
- 明确哪些参考只借鉴原则，不能直接照搬。
- 形成推荐方向。

### 输出

建议新增：

```text
docs/visual-reference-research-YYYY-MM-DD.md
docs/visual-references/screenshots/
```

文档结构：

```text
目标
当前页面诊断
案例列表
每个案例的可借鉴点
需要避免的点
与当前项目对比
推荐方向
下一步原型建议
```

### 质量检查

- 不是简单贴链接，而是有截图和分析。
- 参考案例服务于项目目标，不是追逐视觉噱头。
- 明确当前页面哪些地方需要大改，哪些地方保留。
- 不把单一案例直接变成模板。

## 10. 阶段七：信息架构和交互原型

### 输入

- 数据模型。
- 公开语言规则。
- 视觉参考研究。
- 用户反馈。

### 动作

- 定义页面层级：入口、路线、片库、详情、实验区、方法说明。
- 确定主交互对象：封面、地图、路线、关键词、时间索引、图谱等。
- 降级不适合的交互形式。例如时间轴只能显示发行年份，不能推断内容覆盖年代。
- 先做单个高价值原型，再扩展到全站。
- 对每个交互写明它解决什么问题。

### 推荐结构

1. 首页：强视觉入口，少量说明。
2. 策展路线：帮助读者选择进入方式。
3. 主片库：搜索、标签、排序、详情。
4. 详情页或弹窗：事实、简介、来源、访问渠道。
5. 实验室：图谱、3D、关系探索等附加体验。
6. 方法说明：解释收录标准和来源边界。

### 输出

建议新增：

```text
docs/superpowers/specs/YYYY-MM-DD-content-display-design.md
docs/superpowers/plans/YYYY-MM-DD-content-display-implementation.md
```

### 质量检查

- 交互形式和资料类型匹配。
- 没有为了“酷”而制造幻觉关系。
- 检索层和策展层分工清楚。
- 首页不是说明书。
- 详情信息足够但不过载。

## 11. 阶段八：测试、防回归和质量检查

### 输入

- 数据文件。
- presentation layer。
- 页面原型。
- 用户已确认的原则。

### 动作

- 把关键策展原则写成测试。
- 用测试锁定主目录边界、公开语言、字段完整性、交互约束。
- 对视觉和交互做浏览器截图检查。
- 对链接和资源做基本可访问性检查。
- 每次重要改动后运行全量测试。

### 推荐测试类型

- 数据质量测试：字段、长度、来源、渠道。
- 展示规则测试：标题优先级、标签数量、内部术语扫描。
- 路线测试：人工路线成员、重复限制。
- 时间索引测试：只使用事实年份，不推断跨度。
- 页面测试：资源加载、入口存在、响应式结构。
- 发布前测试：线上链接返回 200。

### 输出

建议新增：

```text
tests/content-quality.test.mjs
tests/presentation-data.test.mjs
tests/app-rendering.test.mjs
tests/app-filtering.test.mjs
tests/routes.test.mjs
```

推荐命令：

```powershell
node --test tests\*.test.mjs
node --check assets\app.js
```

### 质量检查

- 测试覆盖用户明确反复强调的原则。
- 不只测试代码是否运行，还测试内容边界。
- 测试失败时先判断是实现问题还是旧断言过时。
- 不用测试去掩盖未核验事实。

## 12. 阶段九：发布、复盘和 Workflow 更新

### 输入

- 已验证网站。
- README。
- Git 仓库。
- 部署账号。

### 动作

- 清理 `.gitignore`，避免提交临时截图、缓存、部署目录。
- 写简要 README：项目说明、本地预览、数据说明、测试命令、部署链接。
- 如使用 GitHub Pages，添加 `.nojekyll`。
- 推送 GitHub，确认仓库可见性。
- 部署 Netlify 或其他静态托管。
- 验证线上链接。
- 记录复盘，更新 workflow。

### 输出

```text
README.md
.nojekyll
GitHub repo URL
GitHub Pages URL
Netlify URL
docs/project-development-retrospective-YYYY-MM-DD.md
```

### 质量检查

- Git 工作区干净。
- README 中的链接有效。
- GitHub Pages 或 Netlify 返回 200。
- 发布版本包含最新 README。
- 复盘记录实际问题，而不是只写完成事项。

## 13. 批次化执行方式

对于资料量较大的项目，不建议一次性处理全部条目。

推荐批次：

1. 核心样本批：5-10 个最重要条目，用来验证数据模型。
2. 主目录批：按路线、主题或类型分批处理。
3. 延伸目录批：只在主目录稳定后处理。
4. 视觉原型批：每次只重做一个页面层级。
5. 发布批：发布前只做 bug 修复和文档补齐，不再新增大功能。

每批结束都要留下：

- 处理范围。
- 决策记录。
- 未解决问题。
- 测试结果。

## 14. 常见风险和处理

### 风险一：资料被视觉包装后显得过于确定

处理方式：

- 为来源和可靠性保留字段。
- 不确定信息显式标记。
- 不在公开页面写超出来源的判断。

### 风险二：主目录膨胀

处理方式：

- 强制区分核心、重要、延伸、相关议题。
- 每次新增条目都写明进入理由。
- 对边缘条目默认放延伸目录。

### 风险三：自动标签替代策展判断

处理方式：

- 路线成员人工定义。
- 每个条目最多一个主路线和一个辅助路线。
- 搜索和标签只是检索工具，不承担主叙事。

### 风险四：交互产生事实幻觉

处理方式：

- 时间轴只用事实年份。
- 图谱关系必须有证据来源。
- 聚类、连线、距离不能暗示未经验证的因果关系。

### 风险五：Skill 过早固化

处理方式：

- 先把本 workflow 跑过不同资料类型。
- 只沉淀稳定步骤和质量门槛。
- 不把具体项目风格、主题判断和一次性实现写进 skill。

## 15. Skill 化建议

如果要把本 workflow 发展成 Codex skill，建议名称为：

```text
curated-media-atlas
```

Skill 不应该直接承诺“自动做出完整网站”，而应该触发一套严格流程：

1. 资料盘点。
2. 收录标准。
3. 来源核验。
4. 数据模型。
5. 视觉参考研究。
6. 信息架构。
7. 原型实现计划。
8. 测试和发布 checklist。

建议 Skill 目录结构：

```text
curated-media-atlas/
  SKILL.md
  references/
    source-priority.md
    curation-criteria.md
    public-copy-rules.md
    visual-reference-checklist.md
    testing-checklist.md
  templates/
    source-inventory.md
    content-verification-method.md
    visual-reference-research.md
    project-retrospective.md
    readme.md
  scripts/
    validate-json.mjs
    audit-public-copy.mjs
    check-links.mjs
```

优先脚本：

- JSON 字段完整性检查。
- 简介长度和空值检查。
- 内部术语扫描。
- 访问渠道字段检查。
- 线上链接状态检查。

## 16. 用新方向测试本 Workflow

下一次可用“电子音乐类书籍策展清单”测试这套流程。

测试目标：

- 不做网页，先验证资料盘点、收录标准、来源核验和数据模型。
- 核心对象从纪录片改为书籍。
- 观察哪些字段、来源优先级和分类标准需要调整。

书籍方向建议字段：

```text
id
title
original_title
author
year
publisher
isbn
summary
themes
regions
genres
importance_reason
grade_code
collection_visibility
sources
access_channels
```

书籍方向需要新增判断：

- 是否有正式出版信息。
- 是否有可靠馆藏或出版社页。
- 是否属于电子音乐核心主题，还是音乐产业、流行文化或声音艺术延伸。
- 是否适合作为入门阅读、专业研究或边缘补充。

测试产出建议：

```text
docs/electronic-music-books-workflow-test.md
```

测试结束后回答三个问题：

1. 本 workflow 是否适用于书籍资料。
2. 哪些阶段需要为书籍方向调整。
3. 是否已经适合创建正式 skill。
